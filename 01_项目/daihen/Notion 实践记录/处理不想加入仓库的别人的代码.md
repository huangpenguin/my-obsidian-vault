# 处理不想加入仓库的别人的代码

### 子模块（git submodule）

> 由主仓记录外部仓库指针（.gitmodules + commit）。历史整洁，引用明确。其他人 `git submodule update --init --recursive` 即可对齐版本。
> 
- 适用：需要可复现、团队协作、CI
- 注意：维护指针更新

```bash
# 添加与初始化
git submodule add <git-url> third_party/<name>
git submodule update --init --recursive

# 升级子模块版本
cd third_party/<name>
git fetch && git checkout <target>
cd - && git add .gitmodules third_party/<name> && git commit -m "bump <name>"
```

---

### .gitignore（third_party 本地使用）

> 外部工具放到 `third_party/` 并在主仓忽略，仅本地使用；获取由使用者自行完成。
> 
- 适用：个人本地、频繁变更、不需团队对齐
- 注意：可复现性弱，新环境需手动获取

```bash
# 可选：简单获取脚本
mkdir -p third_party
[ -d third_party/<name> ] || git clone <git-url> third_party/<name>
```

---

third_party 下的外部仓库不建议直接当你自己的代码混到同一个 Git 历史里。推荐：

1.Git Submodule（最常见）：把外部仓库以子模块引用，保留其独立版本。

2.Git Subtree（需要把外部库合并到你的仓库，但保留同步能力）

3.Fork 外部仓库到你组织，然后作为 submodule 引用你自己的 fork，便于打补丁和版本锁定。

- 如果你需要对 PaddleOCR 做定制改动：
    - 在你 fork 的仓库里开分支维护改动；
    - 在主项目用 submodule 指向该分支的固定 commit；
    - 这样升级上游时可控，不会破坏你自己的历史。
