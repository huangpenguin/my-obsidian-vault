# 1. 你写的架构基本对，但 MuJoCo / Isaac 的角色要稍微修正

你现在写的是：

> MuJoCo / Isaac 作为前段算法演练与碰撞规划环境  
> → 验证后通过 API 给 FD-ST / DAIHEN controller

更准确应该是：

```
                   前段算法开发
                        │
 Language + 3D Scene   │
          ↓             │
       VLM / AI         │
          ↓             │
     Target Pose        │
          ↓             │
  Geometry / IK / Planner
          │
          ▼
 ┌───────────────────────┐
 │ MuJoCo / Isaac Sim    │
 │ 仿真、Physics、Sensor  │
 │ Algorithm Validation  │
 └───────────────────────┘
          │
          ▼
   Intermediate Format
   Pose / Waypoint / Path
          │
          ▼
 ┌───────────────────────┐
 │ FD-ST                  │
 │ DAIHEN-specific        │
 │ Reachability           │
 │ Collision              │
 │ Program / Tact Check   │
 └───────────────────────┘
          │
          ▼
       实机 Robot
```

其中真正负责：

- IK
- motion planning
- trajectory optimization
- collision-aware planning

更推荐明确放：

```
MoveIt
cuRobo / cuMotion
PINK
自己的 geometry solver
```

而不是笼统说“MuJoCo 做规划”。

MuJoCo 官方定位首先是通用刚体/接触**物理仿真引擎**，特别适合机器人仿真、控制、ML、contact dynamics。

Isaac Sim 则已经直接包含 manipulation motion generation、collision world、cuMotion、IK 等接口，所以如果使用 Isaac，它可以把“Simulation + Planning”整合得更多。

# 2. 所以“前期训练不考虑 FD-ST”基本正确

尤其如果你所谓“训练”是：

### VLA / Policy Training

例如：

```
Atlas / Marble / CAD
       ↓
Isaac Sim / MuJoCo
       ↓
大量 rollout
       ↓
VLA / Policy Training
```

那么：

> **FD-ST 基本不应该进入 training loop。**

原因很简单。

FD-ST 的定位是：

> **DAIHEN 自己的 Offline Teaching + Simulation 系统**

而不是：

> 高并行 RL / VLA training simulator。

DAIHEN 官方介绍 FD-ST 是和其 controller 高度兼容的离线示教系统，可以读取机器人系统 backup data，并使用实际机器人控制软件进行高精度 tact simulation。

所以两者职责完全不同。

这个概念也值得修正。

↓

↓

你完全可能一行训练代码都不写

# 4. FD-ST最适合放在后半段的“DAIHEN-specific validation”

这才是它最大的价值。

例如你的算法生成：

```
P1
(x=108, y=312, z=53,
 rx=0, ry=45, rz=90)

P2
(...)
```

你的 MoveIt / Isaac 认为：

```
✓ IK feasible
✓ no collision
```

但最终最好再问：

```
FD-ST：
这个姿态在真正的 DAIHEN robot model 上成立吗？

这个 program DAIHEN controller 能不能执行？

DAIHEN 的 tool / joint / controller restriction 有没有问题？

实际 tact time 是多少？
```

FD-ST 官方的一个明显价值就是**使用实际 DAIHEN robot control software 做模拟，因此其 tact simulation 与 controller 更接近**。

所以 FD-ST 更像是：

> **Vendor-specific ground truth / final validation layer**

而不是前面的研究 sandbox。

# 7. 最稳的开发流程其实是这样

## Phase 0：第一周就搞清 FD-ST

不是在 FD-ST 里写 AI，而是确认：

```
DAIHEN Robot Model
Controller Model

Base Frame
Tool Frame
TCP

XYZ convention
Orientation convention

Joint limits

Program format

MOVEJ / MOVEL 等命令

FD-ST:
API?
SDK?
CLI?
File Import?
Program Import?
```

然后定义一个自己的**中间格式**。

比如：

```
{
  "frame": "robot_base",
  "tool": "tool_01",
  "poses": [
    {
      "position_mm": [108.0, 312.8, 53.3],
      "orientation_deg": [0, 45, 90],
      "motion": "linear"
    }
  ]
}
```

这就是整个项目非常关键的一层。

# 9. 但是每完成一个 milestone，就用 FD-ST 做一次 cross-check

例如 Month 1：

```
自己生成 10 个 Pose
↓
导入 / 手动输入 FD-ST
↓
比较
```

检查：

```
IK一致吗？
姿态一致吗？
Collision一致吗？
```

---

Month 2：

```
完整 P1 → P2 → P3
↓
FD-ST
↓
simulate
```

---

Month 3：

```
自动生成多个 scenario
↓
FD-ST 批量/半自动确认
```

这样不会最后突然发现：

> “我们自己的 simulator 全对，但 DAIHEN robot 根本不能这样动。”

# 10. 最理想的系统其实应该有两个 Validator

我很推荐这种架构：

```
             Generated Motion
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
 Generic Validator       DAIHEN Validator
          │                   │
 MoveIt / cuRobo           FD-ST
 Isaac / MuJoCo             │
          │                   │
          └─────────┬─────────┘
                    ▼
                 PASS
                    ↓
              Robot Program
```

---

## Generic Validator

方便你开发：

```
IK
Collision
Trajectory
Physics
```

---

## FD-ST

确认：

```
DAIHEN robot specific behavior
Controller compatibility
DAIHEN program semantics
Tact time
```

这两个不是互相替代，而是不同层。
