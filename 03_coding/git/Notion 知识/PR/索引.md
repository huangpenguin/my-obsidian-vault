# PR

vscode左下角选择分支创建新分支

这时候会在main基础上创建一个新的分支，再提交分支，然后在github提交一个pr

[github PR](github%20PR.md)

## 1. PR（Pull Request）是什么？

- PR 是一种**代码变更的合并请求**，它向项目维护者申请：
    
    “请把我这边的改动合并到你们的仓库里。”
    
- PR 通常包含：
    - 改动的代码（一个或多个 commit）
    - 说明文字（为什么改、改了什么、测试方法等）
    - 讨论区（Reviewers可以留言建议、代码讨论）
- PR 是现代开源和团队协作的标准工作流核心。

---

## 2. PR 是从哪里提的？

- **一般情况：**
    
    你从目标项目 fork（复制）一份到自己的账号下（即“你的仓库”），在自己的仓库里创建分支改动，完成后向原项目提交 PR。
    
- **你也可以：**
    
    直接 clone 原仓库，创建分支开发，然后把分支推到原仓库的远程（如果有权限），也能发 PR。
    
- 但是多数开源项目或大团队不允许直接推送到主仓库（无权限），所以 fork 并从自己的仓库提 PR 是最常见也最安全的做法。

---

## 3. 为什么推荐从 fork 的仓库提 PR？

- **权限隔离**：你无权直接修改原仓库，避免误操作。
- **方便管理**：你的 fork 可以自由推送和管理分支。
- **PR 更新方便**：修改后直接 push 到 fork 分支，PR 会自动更新。
- **安全稳定**：原仓库不会因为外部提交导致不稳定。

---

## 4. PR 的简单流程举例（GitHub）

1. 你 fork 一份项目到自己的 GitHub 账号。
2. 在自己仓库中 clone 到本地。
3. 新建分支（如 `feature/new-feature`）开发。
4. 修改、commit、push 到你的 fork 仓库的分支。
5. 在 GitHub 网站上，从你的 fork 的该分支，向原仓库的 `main` 或指定分支创建 Pull Request。
6. 项目维护者审查、讨论、合并。

---

### 最佳实践

### 1 PR 里的“代码定位”本质上靠 **Git 提交历史** ，而不是靠文件夹名字

- **PR= 两个分支（或仓库）之间的 diff**
    
    Git 先找这两条分支的**共同祖先 commit**，再把「祖先 → 源分支」这段改动展示出来。
    
- 因此 **路径基准= 仓库根目录**，PR 里看到的每个文件路径都相对于仓库根。
- 只要两个分支**共享一条提交历史**（哪怕很久以前 fork 的），Git 就能算出差异；文件夹层级变动、文件重命名都会在 diff 里体现出来。

> ➜ 关键条件：必须拥有共同祖先 commit
> 
> 
> 两个完全无关的仓库（没有任何共同历史）之间不能直接开 PR——GitHub/GitLab 会提示「Nothing to compare」。
> 

---

### 2 文件夹结构不同会怎样？

| 场景 | 结果 | 处理方式 |
| --- | --- | --- |
| **A 仓库新增/删除/重命名目录** | diff 会显示「新增文件」「删除文件」「rename」 | 用 `git mv old new` 保留历史或直接 `git add` / `git rm` |
| **大规模重排目录后再提交功能代码** | PR 里会看到两类改动混杂，评审困难 | 通常拆成两个 PR：1) 纯目录迁移2) 功能改动 |
| **源分支基于陈旧的目录布局** | 合并时冲突概率高 | 在发 PR 前先 `git pull --rebase upstream/main` 同步最新结构 |

---

### 3 最佳实践：确保“同一棵树”再提 PR

1. **fork / clone** *目标仓库* → 保证历史一致
2. **紧跟 upstream/main**
    
    ```bash
    git checkout main
    git pull upstream main --ff-only      # 更新本地主分支 就是按钮的pull
    git checkout -b feature/#123_task     # 基于最新主分支切新分支
    ```
    
3. **PR 前先 rebase**
    
    ```bash
    git fetch upstream
    git rebase upstream/main
    # 冲突先解决，再 push --force-with-lease
    
    ```
    
4. **目录重构单独提交** ↔ 功能改动分开展示

---

### 5 结论

- PR 能否比较代码 **取决于共享提交历史**，而非目录是否一致。
- 目录差异只影响 diff 的可读性与冲突概率，不会阻止 PR 本身。
- **先同步 upstream → 后改动 → 再发 PR** 是保证可合并、易评审的基本规则。
