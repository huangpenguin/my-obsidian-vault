以下是目前最主流的几种 API 设计方式，你可以像看“工具箱”一样来了解它们：

---

**🌐 1. REST —— 互联网的“普通话”（最常见）**

- **什么是它**：基于 HTTP 协议，通过网址（URL）和标准的动作（GET、POST、PUT、DELETE）来传输数据。通常返回的是 **JSON** 格式。
- **通俗例子**：你去餐厅看菜单（GET `/menu`），点了一个菜（POST `/order`）。
- **为什么火**：简单、好懂、生态极度成熟。你平时调包用的大多数开源库、第三方云服务，默认提供的都是 REST API。

**⚡ 2. gRPC / RPC —— 追求极致速度的“内部暗号”**

- **什么是它**：由 Google 开发。它不走普通的 HTTP 网页传输，而是把数据压缩成二进制（Protobuf）进行极速传输。它让不同服务器之间调用函数就像调用本地代码一样。
- **为什么 AI 公司爱用**：**AI 模型的推理和计算非常消耗性能**。在 PKSHA 的内部系统里，当一个图像识别服务要把数据传给另一个文本处理服务时，用 REST 会太慢（因为 JSON 体积大、解析慢）。这时候用 gRPC 可以把延迟降到最低，极大提高服务器的吞吐量。

**🔄 3. WebSocket —— 永远在线的“实时通话”**

- **什么是它**：普通的 REST 是“客户端问一句，服务器答一句”。而 WebSocket 是一旦建立连接，双方就可以**同时、持续地、实时地**向对方发送数据。
- **为什么 AI 公司爱用**：想想 ChatGPT 的“打字机”流式效果（Streaming），或者智能客服的实时聊天、工业机器人的数据实时监控。这种**需要服务器不断把最新数据“推”给客户端**的场景，必须用 WebSocket 或者是基于它的技术（如 SSE）。

**📊 4. GraphQL —— 按需索取的“自助餐”**

- **什么是它**：由 Facebook 开发。传统的 REST 你访问一个网址，它会把所有数据都打包给你（不管你想不想看）。而 GraphQL 允许你明确告诉服务器：“我只要名字和价格，其他数据别给我”。
- **为什么有用**：前端开发非常喜欢，能极大减少网络传输的数据量，提高手机端等弱网环境下的加载速度。

---

**🔍 阶段一：从“看懂”到“审查”（把 AI 当你的下属）**

现在写代码，AI 是“操作工”，你必须成为**“总监理”**。

- **严格进行 Code Review（代码审查）**：AI 写完一段代码后，不要直接复制。盯着它看 3 分钟，问自己：
    - 这段代码有没有潜在的 Bug？
    - 如果输入的数据是空的、或者是错的（异常处理），它会崩溃吗？
    - 它的**时间复杂度**和**空间复杂度**是多少？（比如，这个循环在处理 100 万条 AI 推理数据时会不会卡死？）
- **训练方法**：每次让 AI 写完代码，再追问它一句话：“_这段代码有什么潜在的风险，你能帮我写出 5 个测试用例（Test Case）来测试它吗？_”

**🏗️ 阶段二：学习“系统设计”与“架构”（拼积木的游戏）**

AI 擅长写一个具体的函数（单块积木），但不擅长设计整座大楼。软件工程的核心是**系统架构**。

- **掌握经典设计模式**：去了解什么是单例模式、工厂模式、观察者模式。理解为什么要把代码拆分成不同的模块（低耦合、高内聚）。
- **学习系统分层**：写一个 AI 应用时，强迫自己把代码干净地拆成三层：
    1. **数据层 (Data)**：只负责从数据库或 API 读取原始数据。
    2. **业务逻辑层 (Service)**：负责你的 AI 调包、Prompt 组织、模型推理。
    3. **接口层 (Controller)**：负责把结果包装成我们上文聊到的 **REST API** 抛给前端。
- **训练方法**：不要一上来就写代码。先用画图工具（如 Mermaid 或 Excalidraw）画出**系统的数据流向图**和**组件关系图**。架构图对了，再让 AI 去填空每一个函数。

**🛡️ 阶段三：建立“自动化测试”与“CI/CD”的肌肉记忆**

高水平的软件工程师，绝对不是靠嘴说“我的代码没问题”，而是靠**自动化工程**来保证质量。

- **写单元测试 (Unit Test)**：逼自己使用 `pytest` 等工具。AI 写的核心函数，必须有自动化的测试脚本去跑它。
- **玩转 Git 流程**：不要总在 `main` 分支上写代码。练习规范的 Git 工作流：建新分支（Feature Branch） → 提 PR (Pull Request) → 模拟代码合并。
- **训练方法**：尝试在 GitHub 上配置一个极其简单的 **GitHub Actions**。做到只要你一提交代码，系统就会自动帮你运行测试脚本，检查 AI 写的代码有没有被你“改烂”。

**🌐 阶段四：学习“云原生”与“运维”（把代码跑起来）**

- **玩转 Docker**：这是现代软件工程的必修课。尝试把你的 AI 调包程序、依赖项（如 PyTorch、OpenAI SDK）全部打包成一个 **Docker 镜像**。

**📌 第一步：API 设计与环境初始化（训练：API规范与数据验证）**

不要先写模型代码，先规范数据的进出。我们要用 **FastAPI** 搭建标准的 REST API，并用 **Pydantic** 做数据校验（防止坏数据搞崩系统）。

💬 **你可以发给 Cursor 的 Prompt：**

> “我准备用 FastAPI 框架开发一个标准的 REST API 文本摘要服务。请帮我创建项目基础结构，并编写 `main.py`。要求：
> 
> 1. 设计一个 `POST /api/v1/summarize` 接口。
> 2. 使用 Pydantic 定义请求体（Request Body），必须包含 `text`（字符串，限制长度 50 到 10000 字）和 `max_length`（整数，默认 150）。
> 3. 使用 Pydantic 定义标准的返回体（Response Body），包含 `summary`（字符串）、`original_length`（整数）和 `status`（字符串）。

> 2. 重构 `main.py`：让接口层（Controller）去调用 `AIService` 的方法，确保 API 路由文件里不包含具体的模型调用逻辑。”

> 1. **正常用例**：发送合法文本，检查是否返回 200 和预期的 JSON 结构。
> 2. **边界用例**：发送少于 50 字的文本，检查是否触发 400 错误。
> 3. **边界用例**：发送超长文本，检查是否被拦截。
