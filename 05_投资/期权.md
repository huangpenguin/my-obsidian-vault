# 工程模式：远程开发，但训练独立运行

## 1. 你列出的几种模式，应该这样组合

|模式|我的建议|
|---|---|
|本地编辑 + 服务器训练|可以，但避免靠手动复制文件维持一致性|
|Remote-SSH + 服务器容器|**作为你的主开发模式**|
|本地 Dev Container|用于轻量测试、离线阅读等，不必复制完整 GPU 栈|
|远程 Dev Container|**用于交互开发、调试、小规模测试**|
|CI 触发远程任务|**用于自动检查和经过批准的正式实验**|

对你来说，最值得坚持的原则不是“所有东西都进一个容器”，而是：

> **开发容器可以随时重建；正式训练不能因此被打断。**

## 2. 开发容器和训练容器分开

我建议这样组织：

```
Mac：Cursor / VS Code
          │ Remote-SSH
          ▼
Linux 服务器
  ├─ 开发容器
  │    └─ 阅读、编辑、调试、单元测试、小规模 smoke test
  │
  ├─ Coding agent 工作区
  │    ├─ Codex 任务 A
  │    └─ Cursor 任务 B
  │
  ├─ 独立任务管理
  │    ├─ 训练作业
  │    └─ 评估作业
  │
  └─ 持久存储
       ├─ 数据集
       ├─ 实验配置与日志
       └─ Checkpoint、指标和视频
```

开发镜像与训练镜像可以共享同一套锁定的 ML 依赖；开发镜像额外包含调试工具即可，**不必强求两个镜像完全相同**。

GPU 容器仍依赖宿主的 NVIDIA 驱动和容器运行支持，不能把“镜像里有 CUDA”理解成“不需要服务器驱动配置”。[NVIDIA Docs](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)

## 3. 正式训练必须使用冻结的代码

这一点对多 agent 特别重要：

```
Agent 正在修改的 worktree
            ↓ 提交 / 快照
固定 commit + 镜像 + 配置 + 数据版本
            ↓
独立训练作业
```

**不要让长训练直接读取一个仍被 agent 不断修改的工作目录。**

否则可能出现：训练主进程已经启动，但后续动态加载的模块、子进程、配置或评估脚本读到了不同版本。这样的实验很难解释。

## 4. 断线恢复要分三层

|你想恢复的东西|需要什么|
|---|---|
|重新进入服务器|SSH 重连|
|继续一个 coding agent 的上下文|明确的 session ID 和持久会话|
|从中断处继续训练|完整 checkpoint 和框架支持的恢复逻辑|

模型续训通常不仅需要权重，还涉及 optimizer；根据项目，还可能需要 scheduler、AMP scaler、随机数状态、数据采样进度，以及 RL 的 replay buffer、归一化状态等。哪些能完整恢复，必须检查真实代码。[PyTorch Docs](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html?utm_source=chatgpt.com)

对目前的规模，我会先选**现有调度器，或者小型任务服务 + 独立容器**。`tmux` 可以作为手工工作的起点，但不要让它承担全部任务管理职责，也不建议一开始就引入 Kubernetes、Airflow 等整套平台。

# 五、CI 能不能控制服务器训练？可以，但不要把 CI 当成模型训练本身

GitHub Actions 可以使用 self-hosted runner 执行服务器任务，也可以通过受控接口提交远程任务；`workflow_dispatch` 支持手工或 API 触发。[GitHub 文档](https://docs.github.com/en/actions/reference/runners/self-hosted-runners?utm_source=chatgpt.com)

我建议拆成两条流水线：

```
代码 PR
  → 格式与静态检查
  → 单元测试
  → 数据 schema 检查
  → 必要的小规模前向 / GPU smoke test

正式实验
  → 人工批准参数和资源预算
  → 固定 commit、镜像、数据版本
  → 提交服务器训练作业
  → 训练与评估
  → 保存产物
  → 回报最终状态
```

**不建议每次 push 都自动跑完整训练。**

还有一个很容易做错的地方：

> **CI 显示“提交成功”，不等于“训练成功”。**

如果 CI 只是提交一个异步任务，它应该记录 job ID，之后通过任务状态或回调更新最终结果，不能把一个绿色提交步骤当成模型已经训练完成。

测试报告、小日志可以用 GitHub artifacts；大模型、视频和数据产物，我更建议放在公司允许的持久存储中，并记录路径和校验信息。GitHub 官方支持工作流产物的上传、下载与保留管理。[GitHub 文档](https://docs.github.com/actions/writing-workflows/choosing-what-your-workflow-does/storing-and-sharing-data-from-a-workflow?utm_source=chatgpt.com)

安全方面，**不要让不可信 PR、任意评论或 agent 生成的工作流直接获得内部 GPU 主机的无限权限**。Runner 一旦能执行恶意代码，就可能泄露凭据或访问内部资源，private 仓库也不是自动的安全保证。[GitHub 文档](https://docs.github.com/en/actions/concepts/security/compromised-runners?utm_source=chatgpt.com)

# 六、手机控制 agent：你的领导那套方便，但现在可以做得更简单

我认为 **Slack → Hermes → Codex 很适合你的需求**：手机主要用来下达任务、看进度、审批和调整方向，而不是在小屏幕上操作完整 IDE。

但应把两类需求分开：

|需求|优先方案|
|---|---|
|在服务器新开 Codex 任务|Slack → Hermes → 独立 Codex runtime|
|在服务器新开 Cursor 任务|Slack → Cursor 官方 My Machines worker|
|继续已有 Cursor 会话|Cursor 原生 Remote Control|
|继续已有 Codex App 会话|Codex 官方 Remote|
|一个 Hermes 自动统筹所有产品|后续再加适配层，不作为第一阶段|

这些原生能力分别由 Hermes、Cursor 和 OpenAI 当前官方文档支持；它们并不意味着不同产品的聊天记录自动互通。[Hermes Agent](https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime)

## 1. Hermes 放服务器，不放在你的 Mac 上当桥梁

你的目标结构应该是：

```
手机 / Mac 的 Slack
         ↓
服务器上的 Hermes Gateway
         ↓
服务器上的 Codex runtime
         ↓
项目工作区 / 受限任务接口
```

Hermes 的 Slack 接入支持 Socket Mode，通过服务器主动连接 Slack，**不需要为了收消息开放公开 webhook**。服务器必须能访问 Slack 和所选模型服务。[Hermes Agent](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/slack)

所以服务器不需要装 Slack Desktop，也不需要桌面 GUI。

## 2. Hermes 已有 Codex runtime，但别直接碰你现有 daemon

Hermes 当前有可选的 Codex app-server runtime，可以把工具执行交给 Codex。官方文档同时显示，它会启动自己的子进程，并可能迁移或修改 Codex 配置。[Hermes Agent](https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime)

考虑到你已经有运行中的 `app-server --listen unix://` 和会话，我建议：

**保留现有进程不动，为 Hermes 使用独立服务身份或至少独立的 `HERMES_HOME`、`CODEX_HOME`。**

Hermes 官方文档明确提供了通过 `CODEX_HOME` 隔离配置和认证的方式。不要把“支持 app-server”误解成“安装后自动接管你原来 Codex App 的全部会话”。[Hermes Agent](https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime)

## 3. Cursor 不一定需要经过 Hermes：官方已经支持服务器 worker

这是最值得利用的现成功能。

Cursor 的 **Self-Hosted Machines / My Machines** 可以让工具调用在你自己的机器上运行。它的 agent loop 和模型推理仍在 Cursor 云端，但文件修改、命令和测试可以发生在你的服务器。[Cursor](https://cursor.com/docs/cloud-agent/self-hosted)

官方给出的基本启动形态是：

```
agent login

agent worker start \
  --name lab-cursor-1 \
  --worker-dir /实际确认过的项目路径
```

随后在 Slack 中可以指定：

```
@Cursor worker=lab-cursor-1 检查评估脚本，只读，不运行训练。
```

`worker=` 是官方支持的参数，不是需要你自己实现的伪命令。长期运行时，再把 worker 交给服务器服务管理，而不是一直依靠 SSH 终端。[Cursor](https://cursor.com/docs/cloud-agent/self-hosted/my-machines)

于是，你可以在**同一个 Slack 客户端**里这样工作：

```
@Hermes：让 Codex 修复数据加载器。

@Cursor worker=lab-cursor-1：独立审查评估协议。
```

**一个手机入口、两个 bot、各自使用原生执行链路，比先开发跨产品万能控制器更合理。**

需要注意：自托管不等于数据完全不出网。Cursor 官方说明，必要的文件内容、工具输出、diff 和部分产物仍会发送到 Cursor，因此公司代码与数据政策仍需确认。[Cursor](https://cursor.com/docs/cloud-agent/self-hosted)

## 4. 你明确提到的“Cursor IDE 现有会话”，现在也有原生路径

Cursor 当前的 Remote Control 文档说明：

在支持版本的 **Agents Window** 中开启 Remote Control，再在会话里执行：

```
/remote-control
```

然后继续发消息，即可从对应移动入口跟进。当前文档要求 Cursor **3.9.8 或更高版本**及相应账户、组织和隐私设置，并明确支持本地与 Remote SSH 工作区。相关计算机仍需保持可用。[Cursor](https://cursor.com/docs/cloud-agent/mobile)

不过，**Remote-SSH + Dev Container 的嵌套情况，不能仅凭“支持 Remote SSH”就保证你的具体组合一定正常，需要实际验证。**

因此，我会这样选：

> **只是离开桌面一会儿、要继续当前会话：用原生 Remote Control。**  
> **希望 Mac 关掉后，服务器仍独立承担长期 agent 工作：用服务器 My Machines worker。**

Codex 的官方 Remote 也支持从手机继续主机上的工作。当前文档的结构是手机连接已授权的桌面主机，桌面主机还可以连接 SSH 项目；**仅有 Linux app-server，并不代表手机会自动发现它**。不要为此把 app-server 直接暴露到公网。[ChatGPT Learn](https://learn.chatgpt.com/docs/remote-connections)

## 5. 什么时候才让 Hermes 同时管理 Cursor 和 Codex？

当你确实需要这样的能力时：

> “我只发给 Hermes，它自己判断用 Cursor 还是 Codex，然后拆任务、追踪、交叉审查。”

这才值得增加统一调度适配层。

Hermes 官方文档明确指出，把外部 CLI 接成 worker lane 还不是即插即用路径。Cursor CLI 的无界面调用本身是现成功能，但任务状态、日志、取消、恢复、权限和会话映射仍需要适配。[Hermes Agent](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-worker-lanes)

**你的第一阶段没有必要承担这笔维护成本。**

# 七、多 agent 并行，最重要的是隔离和任务边界

我建议先从下面这个规模开始，而不是一下开很多个：

```
Codex：实现修改
Cursor：独立审查或处理另一模块
GPU：先限制一个正式训练槽位
```

这是初始资源策略，不是工具本身的并发上限。

每个写代码任务至少绑定：

```
Slack thread
    ↔ task ID
    ↔ agent 类型和 session ID
    ↔ 独立 worktree / 分支
    ↔ 日志目录
    ↔ 它提交的训练 job ID
```

关键规则是：

**同一会话，同一时间只有一个写入控制者；不同任务不要共用一个可写工作区；不要在并发自动化里用 `resume --last` 猜测要恢复哪个任务。**

人工想接手修改时，先暂停或交接对应 coding task。另一位 agent 的结果通过 commit、PR 和任务说明交接，而不是偷偷改它正在工作的目录。

另外，**Git worktree 不是安全沙箱。** 它能减少文件冲突，但不能自动隔离凭据、GPU、网络和宿主权限。

尤其不要把“容器里运行了 agent”当成绝对安全：如果它能访问宿主 Docker socket 或拥有 Docker 组权限，通常仍拥有很高的宿主控制能力。Docker 官方明确警告，Docker 组权限相当于 root 级权限。[Docker Documentation](https://docs.docker.com/engine/install/linux-postinstall/?utm_source=chatgpt.com)

对你的机器人项目，我还会加一条硬边界：

> **手机 agent 可以修改代码、提交训练和仿真评估，但默认不能直接让真机机械臂动作。**

训练、模型推理和底层机器人控制应分权限；真机部署需要现场授权、明确策略版本和安全联锁。

# 八、可以直接交给部署 agent 的总提示词

我已经把完整内容拆成了三个实施提示词：**A 项目环境与任务层、B Hermes/Codex、C Cursor 官方 worker**。下面这段可以直接作为总任务要求：

```
请为我的 Mac + 无头 Linux 服务器建立可复现的 ML/RL 远程开发和手机多 agent 工作流。

已知：
- 我使用 Cursor/VS Code、Codex App。
- 服务器已存在 Codex app-server（包括 unix:// 监听）和活动会话。
- SSH/VPN 可能断线，长任务必须继续。
- 手机使用 Slack 下达任务、查看进度和审批。
- 保留现有服务，不终止、不重启、不全局升级、不覆盖现有 Codex 配置和认证。

先只读检查：
OS/架构、GPU/驱动、Docker、现有调度器、仓库状态、锁文件、
真实训练/评估入口、checkpoint 恢复能力、现有服务和权限。
不要打印 token、auth.json 或完整环境变量。
未知路径、版本和项目参数不得猜测。

架构要求：
1. 日常开发使用 Remote-SSH + 服务器 Dev Container。
2. 核心计算依赖写入 Dockerfile 和锁文件，不只写在 IDE 初始化钩子里。
3. 正式训练使用固定 commit/快照、image digest、数据版本和配置，
   作为独立作业运行，不读取 agent 正在修改的工作区。
4. 数据默认只读；日志、checkpoint、指标和视频写入持久存储。
5. 训练作业不能依赖 Mac、IDE、SSH 或聊天窗口存活。
6. 优先复用现有调度器；没有时实现最小受限任务接口。
   不无故引入 Kubernetes 或整套工作流平台。

手机控制：
7. Codex 使用服务器 Hermes + Slack Socket Mode。
   优先独立服务用户，至少隔离 HERMES_HOME 和 CODEX_HOME。
   启用 Codex runtime 前核实其配置写入范围，不影响现有 daemon。
8. Cursor 优先使用官方 My Machines / self-hosted worker，
   通过官方 Slack 的 worker=名称指定服务器。
   不先编写 Hermes 接管 Cursor 的适配器。
9. 已有桌面会话的手机接续另用各产品官方 Remote 功能；
   不把新建 worker 会话宣称为恢复了原来的 IDE/App 会话。
10. 不公开 app-server、Docker socket 或无认证控制接口。
    先确认公司对模型服务、Slack 和数据出站的政策。

多 agent：
11. 每个 coding task 独立 worktree、分支、session ID、日志。
12. Slack thread 与 task/session/workspace/job 明确绑定。
13. 同一会话只能有一个写入控制者；人工接手必须交接。
14. 初始最多 2 个 coding task、1 个正式 GPU 训练任务，
    再依据资源和授权调整。
15. Agent 停止与训练取消是不同操作，不得误杀其他任务。
16. 事件去重；服务重启后先核对真实作业状态，不重复提交训练。

CI：
17. PR 只做获准的轻量检查。
18. 正式训练通过受保护的手工触发，调用同一任务接口。
19. 区分提交成功和训练成功，保存最终退出码与产物索引。
20. 不可信 PR 不进入持有内部数据和高权限凭据的 GPU runner。

验收：
- 远程容器内解释器、依赖、挂载和 GPU 最小测试。
- 两类 agent 实际执行在正确服务器和独立目录。
- 断开 Mac/SSH 后独立测试任务继续。
- Gateway/worker 重启不重复启动训练。
- checkpoint 恢复范围有实际验证。
- 未授权用户、错误项目和超限资源请求不能执行。
- 原有 Codex 服务和配置未受影响。

不要运行完整训练或真机动作来验收。
需要 OAuth、Slack token、组织批准或管理员权限时，
明确说明最小人工步骤，不伪造成功。

最终交付：
配置与代码 diff、真实版本和服务名、实际测试日志、
中文操作手册、停止/恢复/升级/回滚步骤，以及未完成事项。
```

# 九、你的日常操作方式

## 在电脑前

使用 Remote-SSH 打开服务器项目，再进入开发容器。阅读、修改和调试都在这里完成。

准备正式实验时，先固定代码版本和配置，再通过任务入口提交。**不要把“在 IDE 终端里启动一个 Python 进程”当成正式任务管理。**

## 离开电脑后

给 Codex 的任务可以这样写：

```
@Hermes 为项目 XXX 新建独立 Codex 任务。
目标：修复数据加载器的空 episode 异常。
只修改数据模块和相关测试，不改训练超参数。
先跑 CPU 测试，不启动正式训练。
返回 task ID、分支、diff 摘要、测试命令和退出码。
```

给 Cursor 的任务可以这样写：

```
@Cursor worker=lab-cursor-1
独立审查评估脚本的数据划分、seed、终止条件和指标统计。
只读，不修改代码，不运行训练。
返回问题位置、证据和建议。
```

后者需要先完成官方 worker 注册和 Slack 集成，机器名称换成实际名称。[Cursor](https://cursor.com/docs/integrations/slack)

## 要开始训练时

先让它生成计划，而不是直接开跑：

```
为本次修改准备训练计划，但暂不提交。
返回 commit、镜像 digest、数据版本、配置、seed、
资源预算、输出目录、checkpoint 周期和停止方式。
```

确认之后再按**明确的计划 ID**批准。

## 断线之后

先查询原 task ID / job ID，不要重新发送一次“开始训练”。

Agent 会话、服务器连接和模型续训分别恢复。模型是否真的续训成功，要看恢复的训练步数、状态和日志，而不是只看 agent 回复“已经继续”。

Hermes 当前 Slack 文档提供线程内 `!help`、`!status`、`!stop` 等命令形式；但 **`!stop` 停止聊天任务，不应被当成取消独立训练的替代操作**
