我们可以把之前的生图流水线，无缝平移到这个 OCR 自动化流水线中，看看架构有多完美：

1. 核心 Agent 角色平移对照

|模块 / 角色|之前的“生图流水线” 🎨|现在的“工业级 OCR 自动化流水线” 📄|
|---|---|---|
|**输入数据**|提示词模板 + 随机数。|上万张待识别的**原始票据/合同/扫描件图片（或 PDF 抽帧）**。|
|**核心执行器 (Generator)**|调用 Imagen 3 **生成**图片。|调用 **Azure OCR 或 Gemini Vision** 传入图片，**提取并输出**结构化文本（如 JSON）。|
|**质量把控 (Vision QA)**|检查图片里数字清不清晰、有没有穿模。|**交叉审计 Agent**：检查提取出来的 JSON 数据是否符合业务逻辑（例如：发票上的 `单价 * 数量` 是否等于 `总金额`？提取的日期格式对不对？关键字段是不是空的？）。|
|**调度控制 (Orchestrator)**|失败后修改 Prompt 重新生图。|如果 QA 审计发现金额对不上，调度 Agent 重新把图打包发给一个更强大的模型（如 GPT-4o 或 Claude 3.5），并附带报错：“上一次计算对不上，请重新核对图中的数字”。|

2. 外围工程架构（异步、限流、断点续传）为什么完全不需要变？

- **高并发限流（Rate Limits）**：Azure API 或 谷歌 API 同样有严格的 QPS 限制。当客户扔给你 5 万张医疗发票需要处理时，你依然必须用 `asyncio.Semaphore` 控频，用 `tenacity` 应对 429 报错，否则程序一定会挂。
- **断点续传状态机**：处理 5 万张图，网络必然会断，大模型必然会偶尔超时。你的 SQLite/PostgreSQL 状态机此时价值连城。如果跑到第 12000 张发票时断网，重启后系统自动扫描 `status='PENDING'` 的发票继续识别，**绝对不让客户为已经识别过的发票重复付 API 钱**。
- **内存流式处理**：发票图片从客户上传，到送入 Azure OCR，再到审计，全程在内存中以二进制流处理，速度极快。
